Pivot · View Markets V2 · Architecture note

One engine, many strategies

Why the Expression layer is a handful of shared Python files — and how that same shared code still produces a genuinely independent analysis and construction for every single strategy.

backend/view_markets/expressions/  ·  ~21 archetypes × 3 tiers → 13 files, not 60
The one-sentence answer. The strategies do not each get their own file. The files are generic machinery; what makes each strategy independent is the data and inputs that flow through them — a declarative catalog entry (which recipe), a set of tier knobs (how aggressive), the view's own resolved instruments (which real stocks/legs), and a delegation to the real analysis engine (greeks, cointegration, weighting) that does the actual, separate maths per strategy.

1The problem we were avoiding

A "strategy" in View Markets is an archetype × tier pair. There are ~21 archetypes (rate debit-spread, NBFC-vs-bank pair, event straddle, IV-crush iron-fly, PEAD, merger-arb, cointegrated pair, sector-vs-index, factor-ETF-vs-index, purity basket, factor-tilt, multi-asset, the six MCX commodity families…) and each can be expressed Conservative / Balanced / Aggressive.

That is ~60 concrete variants. The naïve design — one .py per strategy — would mean 60 files that 90% duplicate each other (every one re-implements price loading, weighting, risk, disclosures), drift apart over time, and make a fix in "how we size a basket" a 20-file edit. The repo already rejected that pattern elsewhere (option_strategies.TEMPLATES, weighting scheme-dispatch), so View Markets follows the same rule:

A strategy's difference lives in DATA (a frozen catalog entry + tier knobs), never in a bespoke file. ~60 variants collapse to one data table + five builders + one dispatcher.

2The shared files — and what kind of thing each one is

Every file under expressions/ falls into one of three roles. This is the whole engine:

DATA  facts & settings, no logic MACHINERY  generic glue, runs for every strategy DELEGATES  calls the real analysis engine
FileRoleWhat it holds / does (the same for every strategy)

builders/

3How one request flows through the shared machinery

dispatch.suggest_expressions(view) runs this fixed algorithm for every view. Nothing here is strategy-specific code — the inputs at each step are what differ.

1
Pick archetypes
For each tier, an ordered preference list (the per-tier structure menu) ∩ catalog.archetypes_for_view_type(view.view_type) ∩ an applies_when gate. Exactly one archetype is built per tier → a clean 3-rung ladder, not a flood.
dispatch.py · catalog.py
2
Look up the builder + the knobs
builders.BUILDERS[archetype.expression_kind] and tiers.tier_knobs(kind, tier). Same builder for every "basket" strategy; the knobs differ by tier.
builders/ · tiers.py
3
Resolve the view's REAL instruments
From the belief itself — thematic_map scenario → transmission edges → sector_universe — never fabricated. This is where IT becomes REC/Adani-Power/RVNL and Monsoon becomes Britannia/MRF/Marico.
thematic_map · sector_universe
4
Build — by delegating to the real engine
The builder calls the actual analysis engine with those inputs. It either returns a constructed envelope, degrades honestly to AVOID (thin data / un-shortable), or raises → dispatch falls through to the next preference.
option_strategies · backtest.pairs · weighting · screens
5
Attach timing
timing.timing_to_trigger(view, mode) — Conservative=Confirmation, Balanced=Hybrid, Aggressive=Pre-position. Describes an armed workflow; never creates one. Register-not-execute preserved.
timing.py
6
Enforce the five disclosures, then persist
Fill rationale / risk / capital / historical-strength / horizon (raise if any blank), write one ViewExpression row per tier. Does not commit — the caller owns the transaction.
config_schema.py · models

4So where does the independence come from?

Independence is not produced by separate code. It is produced by five axes of variation that feed the shared machinery. Change any of them and the same builder yields a completely different, separately-analysed strategy.

Axis 1 · the catalog entry

Which recipe — builder, template, params, guards

Two strategies routed to the same option builder are different because their catalog entries carry a different template_or_scheme (bull_call_spread vs iron_condor vs straddle) and different params. The entry is data; it selects the behaviour.

Axis 2 · the tier knobs

How aggressive — same archetype, different dials

Conservative vs Balanced vs Aggressive of one archetype run through the same builder with different option_moneyness / hedge_ratio / single_name_cap / pair_z_* / leverage. Same kitchen, different settings → a different, defended construction per rung.

Axis 3 · the view's resolved instruments

Which real stocks & legs — drawn from the belief, never invented

Step 3 resolves each belief's own symbols from thematic_map → sector_universe. The basket builder is one piece of code; the members it weights are the IT view's domestic names, or the Monsoon view's rural names — per view, grounded, never fabricated.

Axis 4 · delegation to the real engine

The actual maths is separate, per strategy

This is the crux. A builder never contains the analysis — it hands the inputs to the real engine, which runs that strategy's own computation: option greeks / POP / margin (option_strategies), pair cointegration / z-bands / beta-hedge (backtest.pairs), basket weighting + purity + liquidity screens (weighting + screens). Each strategy therefore gets its own independent backtest, its own greeks, its own cointegration test — even though the routing code is shared.

Axis 5 · honest degradation & fall-through

Each outcome is decided by that strategy's real data

A builder can return AVOID (un-shortable name, thin chain) or raise so dispatch tries the next preference. So whether a tier even exists, and what it becomes, is determined independently by whether this strategy's real data supports it — which is exactly why the Crude view has no finished basket while Monsoon has three full tiers.

5Worked example — same code, three independent strategies

The Monsoon view ran through the one pipeline and produced three genuinely different expressions. Same dispatch, same files — different data at each axis, different engine doing the maths:

TierArchetype → builderEngine that did the mathsResult (its own backtest)
Conservativepurity basket → basket_builderweighting + screens (equal-weight, single-name cap)+45.5% vs Nifty +14.9%

Three rows, one engine. The basket and the pair share members but are analysed by different engines (weighting vs cointegration) and so behave independently; the option is a different kind entirely. None of this required a "monsoon_conservative.py".

The mental model. Think of a kitchen with a recipe book. The kitchen (dispatch + builders) is shared. Each dish is defined by its recipe card (catalog entry), the dial settings on the equipment (tier knobs), and the ingredients delivered for this order (the view's resolved instruments). The recipe says which specialist station cooks it (delegate to the real engine). Same kitchen, different cards + ingredients + stations → distinct, independently-prepared dishes. Adding a new dish is a new recipe card, not a new kitchen.

6Why this is the right trade

What "shared" buys us

  • One place to fix. Improve basket sizing, the short rule, or the disclosure gate once — every strategy inherits it.
  • No drift. 60 hand-written files would diverge; one table + five builders cannot.
  • Add by data. A new strategy is a new catalog row (+ knobs if a new kind), not new code.
  • Honesty enforced centrally. Register-not-execute, the AVOID rule, the five mandatory disclosures, and never-fabricate all live in the shared layer, so no strategy can quietly skip them.

How "independent" is guaranteed

  • Different recipe → different builder/template/params.
  • Different dials → different tier construction.
  • Different ingredients → the view's own real instruments.
  • Different specialist → the real engine runs that strategy's own greeks / cointegration / weighting / backtest.
  • Different verdict → honest degradation decides per-strategy whether a tier exists at all.
In one line: shared code, independent data + inputs + delegated maths. The files are common so we maintain the discipline once; the analysis is independent because each strategy carries its own recipe, dials, instruments, and runs through its own real analysis engine.

Where this lives in the codebase: pivot/backend/view_markets/expressions/ — dispatch.py (orchestrator), catalog.py + tiers.py (data), builders/{basket,pair,option,hedge,multi_asset}_builder.py (delegating builders), plus screens.py · honest_short.py · cross_sectional.py · merger_arb.py · timing.py · config_schema.py · commodities.py.
