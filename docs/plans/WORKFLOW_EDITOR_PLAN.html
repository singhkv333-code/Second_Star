PIVOT · LIVING SPEC

The workflow editor needs real connection logic — and an honest catalog.

Today the side editor lets you drop any step next to any step. A stop-loss with no position, a comparison that references a fetch that doesn't exist yet — all pass silently and only blow up when the automation actually runs. And the 49 step types carry jargon-y, sometimes misleading names.

This document is both the explanation and the source of execution: the capability rules and the renamed catalog below are authored here first, then ported verbatim into the backend. The simulator is live — build a sequence and watch what becomes valid.

Model: linear pipeline (Zapier-like) Strictness: hybrid (hard-block only the impossible) Names: labels + groups, IDs unchanged 49 step types · 6 categories

01The two problems

Both are real today and both are visible to the user in the right-side editor (AgentPanel → workflow-editor-mock).

① No connection logic

The only placement rule is "trigger goes first," enforced purely in the front-end picker. Everything else is a free-for-all: invalid arrangements pass validation and surface as a runtime RefNotFoundError or a no-op. There is no notion of what may legally follow what.

② 49 steps, weak names

arm_ipo_intent, trigger.compound, squareoff, allocate_basket vs allocate_notional — jargon and near-duplicates. "Place option strategy" says place but a live order only registers. Useful affordances (formulas, the visual condition builder, paper-vs-live) are buried in code docstrings.

The lever: every fetch/action already declares an output_schema (JSON Schema) in the registry. We type-check references against it and derive "what this step produces" from it — instead of inventing a new type system.

02How the good builders do it

Three reference points — and why Pivot borrows the idea (typed compatibility) but not the shape (we are flat, they are trees/graphs).

BuilderShapeHow it constrainsWhat we take
Composer
systematic investing
 Typed tree of blocks (Weight / If-Else / Filter / Sort / Asset) Each block has typed slots; only type-compatible blocks fit a slot — you can't drop an asset where a condition belongs. The principle that a slot accepts only a defined set of things.
n8n
general automation
 Directed graph of nodes Nodes declare typed input/output ports; the canvas refuses to connect incompatible ports. Triggers have no input. Typed produce/consume — but expressed as pre/post-conditions over order, since our array order is the wiring (no edges to draw).
Zapier
linear automation
 Linear: 1 trigger + N actions Trigger first; each action maps fields from prior steps only. Exactly Pivot's model. We add the missing layer: preconditions per step.
Decision: Pivot is a linear pipeline. So instead of ports or slots, each step declares what it produces into an accumulated world-state and what it requires from it. One pass down the list = full validation. This is just the existing dsl/validators.semantic_validate(allow_position=…) precedent, generalized from one flag to a tag-set.

03The capability model

A step produces capability tags, requires tags from earlier steps (or from your ambient portfolio), and may consume (clear) them. A single linear pass accumulates the produced tags; each step's requirements must be satisfiable by what came before. A trigger at index > 0 starts a new branch and resets the state.

Capability vocabulary

Why "requires position" is a warning, not an error

Your holdings live outside the workflow (ambient state). A "close my Reliance position" automation is perfectly valid even with no opening step — you may already hold it. So a missing position is a warning with a reason ("needs a position — you may already hold it"), never a hard block. Toggle Assume portfolio in the simulator to see this flip.

04Severity & diagnostics

One lint_workflow(steps, ambient?) returns a list of Diagnostic objects. Three severities — only errors ever block saving/activating.

🔴 error

Graph-internal contradictions: non-trigger at index 0; reference to a later/missing step; reference to a field absent from the producing step's output_schema, or with the wrong type; unknown step type.

Blocks activation ✓

🟠 warning

Likely-wrong but legitimately possible: a requires position / pending_orders unmet by earlier steps and not guaranteed by your portfolio. Renders as "needs setup."

Never blocks ✗

🔵 info

Advisory nudges: a branch with no action or notify does nothing useful; a reference into a loose array/object subtree we can't type-check (downgraded, no false positive).

Never blocks ✗

Diagnostic shape

Diagnostic = {
  step_index:   int,
  severity:     "error" | "warning" | "info",
  code:         "ref_forward" | "ref_bad_path" | "ref_type" |
                "needs_position" | "needs_pending_orders" |
                "trigger_placement" | "empty_branch" | "dead_branch",
  message:      str,          // human-readable, shown on the step card
  field?:       str,          // the offending config field, if any
  suggested_fix?: str         // one-click apply target (Phase 4)
}

06Renamed catalog — all 49 steps

Every step keeps its step_type ID (no migration). What changes: the label, the description, and a new sub-group so the picker is navigable. Old label shown struck through. Produce/require/consume tags drive the connection logic above.

07Architecture & API surface

Backend — one source of truth

New pure module pivot/backend/workflows/compat.py:

  • CAPABILITY_RULES — side table keyed by step_type (zero edits to 49 decorators; missing = permissive).
  • lint_workflow(steps, ambient?) → list[Diagnostic] — three passes: structural → ref type-check → capability.

Reuses refs.py (ref regex), each step's output_schema, and the semantic_validate precedent.

The minimal API surface

  • GET /api/step-types — each step gains a compat block + group; bump CATALOG_VERSION.
  • POST /api/workflows/lint — {steps, ambient?} → {diagnostics}; shared with the validators (no rule drift).
  • Diagnostics also returned in the propose draft + workflow GET.

FE: the picker uses catalog.compat for instant buckets; a 250 ms debounced /lint call is authoritative for ref type-checking. Drag-reorder warns inline — only the trigger slot snaps back.
