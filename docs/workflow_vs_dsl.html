Workflows, the DSL, and the four words that get mixed up

propose_workflow and propose_dsl_workflow are two chat-side builders that produce different shapes of draft. trigger.compound and trigger.manual are two trigger primitives that live inside the orchestration system. They get confused because they sit at different layers — this doc separates the layers and shows what fires when.

1 · The four things, one card each

Chat-side builder

propose_workflow

The general-purpose builder. The LLM emits a full steps[] list (one trigger at index 0, optional later triggers start new branches). Every step is a registered step type with a Pydantic config model. Rich action surface, multi-branch, cross-step refs via Mustache.

Produced shape: a workflow_draft_card with a flat steps[] list. Activated, it persists to the Workflow / WorkflowStep tables and the scheduler / watcher pick it up.

Chat-side builder

propose_dsl_workflow

A narrow builder for expressive entry conditions. Emits a workflow with exactly two steps: trigger.compound carrying a DSL tree + one action step. The chat LLM hands the user's natural language straight through; a server-side translator builds the tree.

Produced shape: a workflow_draft_card with two steps. The only action that actually executes today is notify.message; order.register is emitted but has no registered handler.

Step primitive · trigger

trigger.compound

One trigger step type inside the steps[] system. Its config.entry is a DSL tree. The runtime watcher (scheduler.py) walks the tree every tick; when the tree transitions to TRUE, the workflow fires.

This is the integration seam between the DSL expression language and the steps[] orchestration language.

Step primitive · trigger

trigger.manual

A no-op trigger. The workflow fires only when the user clicks Run now on the agent panel. There is no watcher and no schedule.

Hard-blocked by the backtester (workflow_backtester.py:141) because there is no historical signal to replay.

2 · The orthogonal axes inside a workflow

Every steps[] workflow is a sequence of steps drawn from six categories. The categories are different roles, not different formats — read them this way to stop mixing them up.

trigger.*
When the workflow fires. Exactly one trigger at index 0; additional trigger.* later in the list start new branches (one workflow can hold "buy at open AND sell at close" as two triggers).
scheduleprice indicatorcompound eventmanual polymarketmarket_relative_time webhook
fetch.*
Pure reads. Pull data into the step context so later conditions / actions can reference it via {{ context.<idx>.<field> }}. No side effect, no broker call.
quoteindicator fundamentalportfolio intraday_pnlnews day_openprior_close rolling_highrolling_low spread_z_scorerelative_threshold screenertop_movers
condition.*
Boolean gates. Halt the branch when false. Chained condition.* steps in series are an implicit AND. The branch's actions only run if every condition along the way returns true.
numericboolean market_statusposition time_window
action.*
Side effects. The doing half — places, cancels, modifies, allocates. These are the steps the broker / risk layer actually sees.
place_ordercancel_orders set_stoplossset_takeprofit allocate_basketallocate_notional squareoff_allsquareoff_all_intraday squareoff_symbolupdate_watchlist
notify.* / wait.* / control.*
Glue. User-facing messages, in-app log, human approval gates, time delays, conditional skips.
notify.messagenotify.log wait.approvalwait.delay control.skip_if
Pivot fact to remember. Triggers, fetches, conditions and actions are not interchangeable — they're a pipeline. trigger.* → (fetch.* + condition.*)* → action.* → notify.*. A workflow with no action.* step is a watch-and-notify agent, not a trader.

3 · What fires when

trigger.schedule
APScheduler cron. Fires at the configured cron expression in the configured timezone (default IST). Each fire creates one WorkflowRun and walks the branch.
trigger.market_relative_time
Same scheduler, but the cron is resolved from an anchor (open / close / pre_open / post_close) + signed minute offset. "30 minutes before close" → resolves to a concrete cron at activation.
trigger.price
Watcher polls live quotes every tick (scheduler.py:_evaluate_price_trigger). Fires the first tick the threshold is crossed in the configured direction; stores the last value on the step's config so it doesn't re-fire on each tick while above.
trigger.indicator
Watcher computes one indicator (scheduler.py:_evaluate_indicator_trigger) and applies the same threshold logic as price. Per-workflow cost: a yfinance pull + indicator math each tick.
trigger.compound
Watcher walks the DSL tree (scheduler.py:_evaluate_compound_trigger) using the live DataAccessor. Fires when the tree transitions to Ternary.TRUE. crosses_above / crosses_below state lives in cfg["_last_values"] between ticks.
trigger.event
One news fetch + classify pass on each scheduler invocation (today's wiring delegates to fetch.news). Fires when the matched / max_confidence aggregate clears the threshold.
trigger.polymarket
News-events worker holds an open CLOB websocket subscription. Fires when the YES probability crosses the configured threshold (mode=threshold) or when the market resolves (mode=resolution).
trigger.webhook
External HTTP POST to the webhook endpoint. Fires per inbound request that matches the workflow's webhook secret.
trigger.manual
Never fires automatically. Only fires when the user clicks Run now on the agent panel. The run row carries triggered_by='manual'.
Why screenshot 1's "Saved & activated · 0 seconds · Succeeded" is the silent-failure mode. A trigger.manual workflow with fetch + condition + buy fires on activation, evaluates the condition against the market state at that instant, and places the trade if true. There is no future fire — the agent doesn't watch the crossover at all.

4 · propose_workflow vs propose_dsl_workflow

Capability propose_workflow propose_dsl_workflow
Output shape Full steps[] list, any registered step types Exactly 2 steps: trigger.compound + one action
Trigger expressiveness One indicator vs FIXED constant; one price level; one cron; etc. Full 14-node DSL tree (logic, math, aggregates, crossovers, cross-symbol)
Indicator-vs-indicator crossings Workaround: 2x fetch.indicator + condition.numeric Native — comparison(crosses_above, indicator(SMA,20), indicator(SMA,50))
Multi-output indicator components (BB upper/lower, MACD signal) Not addressable via the flat catalog IndicatorNode(component="lower")
Aggregators (percentrank, zscore, barssince, correlation) No equivalent fetch.* type First-class AggregateNode
Cross-symbol spreads / pairs fetch.spread_z_score only Native SpreadNode + arbitrary math
Bar-offset reads (Pine [N]) No offset field on indicator / price / volume
Kleene UNKNOWN handling for missing data Stalls on missing data Three-valued logic — UNKNOWN propagates, no spurious fires
Multi-branch (e.g. buy at open + sell at close) Yes — multiple trigger.* in one workflow No — one trigger, one action
Real order placement (place / SL / TP / cancel) action.place_order, action.set_stoploss, etc. Stub today — only notify.message is wired; order.register has no handler
Portfolio-state reads (resolve "my entire INFY holding") fetch.portfolio + Mustache ref No portfolio node in the DSL
News / Polymarket / approval / delay Yes No
Sector basket / screener fetch.screener + action.allocate_notional No
The DSL is an expression language (one boolean output). steps[] is an orchestration language (a typed sequence of effects). Conditions compose because they're pure reads with one return type; actions don't, because they're side-effecting and order-dependent. That's why propose_dsl_workflow is narrow on purpose — and why trigger.compound exists, to use the DSL inside a steps[] workflow.

5 · trigger.compound vs trigger.manual

trigger.compound trigger.manual
Role Event-driven — fires automatically when its DSL tree transitions to TRUE. User-driven — fires only on a "Run now" button click.
What it watches Live market data via the scheduler's per-tick walk (_evaluate_compound_trigger). Nothing. There is no watcher.
State Threads _last_values on the step's config so crosses_above / crosses_below detect transitions instead of re-firing every tick. None.
Backtestable? Not yet — listed in the watcher (scheduler.py:464) but NOT in _BACKTESTABLE_TRIGGERS (workflow_backtester.py:85). Hard-blocked. Error string lives at workflow_backtester.py:141: "trigger.manual fires when you click 'Run now' — there's no historical signal to replay."
When you'd pick it The whole workflow should auto-fire on a market condition — any crossover, multi-condition, aggregator, cross-symbol or multi-output-component shape. You want a committed, one-shot operation behind a button. E.g. "Sell my entire RELIANCE holding" packaged as a card the user clicks to fire.
The bug pattern — Used as a fallback when the LLM couldn't express the user's automatic condition. Result: workflow fires once at activation (silently buying / selling against current market state) and never again.

6 · Triggers vs Conditions vs Actions — the easy mistake

Trigger Condition Action
Role Wakes the workflow up. When. Gates the branch. If. Does something irreversible. What.
Cardinality per workflow ≥1 (each starts a branch). 0..N per branch, evaluated in series (implicit AND). 0..N per branch, run in order if every condition passes.
Side effect? No (just emits a wake-up event). No (pure boolean). Yes (broker call, position change, watchlist write).
Failure semantics If the trigger source is down (yfinance error), nothing fires. Returns false → branch halts cleanly, no run row failure. Raises → run row is marked failed; broker reject surfaces in run history.
Backtest replay Replayed by the eligibility-checked engine (_BACKTESTABLE_TRIGGERS). Re-evaluated against historical bars at each fire. Filled at next bar's open (default) or bar low for stop-loss.
Examples trigger.schedule, trigger.compound, trigger.manual condition.numeric, condition.market_status, condition.time_window action.place_order, action.set_stoploss, action.allocate_notional

Fetches are a fourth role — pure reads that produce data for conditions and actions to reference. They're not "small triggers" and they don't gate anything; they just populate the step context.

8 · Cheat sheet — which builder for which prompt

Use propose_workflow when …

  • Two or more branches: "buy at open AND sell at close".
  • The action needs portfolio state: "sell my entire INFY when …".
  • News / Polymarket / approval / delay anywhere in the flow.
  • Sector basket / screener allocations.
  • Single-threshold triggers: "RSI < 30, buy 10 INFY".

Use propose_dsl_workflow when …

  • Indicator-vs-indicator crossover (20-SMA crosses above 50-SMA).
  • Multi-output components (price breaks lower Bollinger band).
  • Aggregator-based conditions (price in top decile of 252-day range).
  • Cross-symbol spreads (TCS/INFY ratio z-score > 2).
  • Multi-condition AND / OR / NOT (RSI < 30 AND MACD line > signal AND price > 200-EMA).
  • And the action is just a notification — until order.register has a real handler, anything that needs to place an order should still go through propose_workflow + trigger.compound.

Use trigger.compound (inside propose_workflow) when …

  • You want the DSL expressiveness and a real order leg. This is the seam: rich trigger, rich action surface, same draft card.

Use trigger.manual when …

  • The user explicitly wants a one-shot button they'll click. Examples: "sell my entire RELIANCE holding", "set a 2% SL on my INFY".
  • NEVER as a fallback when the condition is too rich to express — that's the silent-trade bug.
