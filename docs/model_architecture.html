Error → LLM feedback paths

propose_workflow & backtest_workflow — self-correction (max 2 attempts)

Validation error gets appended to messages as a function_call_output. The loop iterates. The model sees its own malformed call + the validator's complaint and emits a corrected draft on hop 2. Counter: _PROPOSE_WORKFLOW_MAX_ATTEMPTS = 2.

Why these two only: they share the steps[] schema; common failures (unknown step_type, step 0 isn't a trigger.*) are mechanical and one-shot self-fixable.

Out-of-retries on propose_workflow → macro fallback

_try_macro_fallback(message) tries to coerce the user's ask into a simpler macro shape with the trigger forced to manual. User gets a draft they can edit instead of a dead end.

All other tools — no LLM retry

Failure is rendered via _format_recoverable_failure_question(tool_name, error, user_message) — a deterministic template keyed on tool name + error class. When the template returns _LLM_CLARIFY_SENTINEL we make a small LLM call (_llm_clarification) for a tailored question. Either way: user sees a specific clarification, no 2–6 s retry burn.

Completeness / ASK_USER — surface + stash

When a tool returns needs_clarification=True with a question, the question is written into history and a PendingToolCall is stashed (tool name, partial args, missing field, type, enum). The next user reply is type-coerced and the tool re-runs with no LLM hop. Cancel keywords (cancel / discard / nevermind) clear both pending and active draft.

Repeat-fallback variation

If the same canned reject would fire two turns running, _is_repeat_fallback swaps in a reset prompt — the user doesn't get the same line twice.

Transport / non-200 errors

LLMOpenAI.complete never raises out of the call site — transport errors become finish_reason="error" responses with a body preview. Cost ledger skips zero-token rows so an error that never reached generation doesn't pollute the spend ledger.

Telemetry — every LLM call leaves a row

One CallTrace wraps every call to LLMOpenAI.complete (and stream_openai). On __exit__ it:

  • Writes a verbose JSONL trace record to PIVOT_LLM_TRACE (opt-in, PII-bearing).
  • Calls record_llm_usage(...) — always on. Opens its own short-lived SessionLocal() (since the trace can close outside any FastAPI request scope), inserts one row in llm_usage, emits a structured event="llm.usage" log line.
  • Swallows every exception locally. Cost tracking can never break an LLM call.
